| 属性 | 值 |
|------|----|
| 日期 | 2026-08-19 |
| 适用 | Pi Web 界面里所有「说一句就消失」的反馈 |
| 落点 | 本文件为长期规范；施工账本见 [R20260819-12](../01-Projects/R20260819-12-统一Toast消息/00-README.md) |
| 协作入口 | 根目录 `AGENTS.md`「统一 Toast」节 |

本文写人（和智能体）**应该怎么想、怎么做、为什么这样做**。API 细节以代码为准：`useToast()` / `lib/toast.ts`。

---

## 1. 先想清楚：控件是动词，结果去 Toast

菜单、按钮、下拉的职责是**让人点一件事**。点完之后「做成了 / 做不成 / 失败了」是另一件事。

若把结果写回控件本身（菜单字变成「标题已更新」、下拉里出现斜体空说明），控件就不再是动词，人会以为菜单坏了，或要再点一次才能读完那句话。

统一做法：**瞬时、可消失的反馈只走一套 Toast**。挂在**文档区顶部居中**，胶囊形说一句，然后自己消失。

---

## 2. 什么时候用 Toast

| 用 | 不用 |
|----|------|
| 现在做不成（无分支、会话未保存、还没消息） | 浏览器系统通知（任务完成、需要注意）——走 `lib/browser-notifications.ts` |
| 手动操作刚成功或失败（生成标题、后续同类动作） | 按钮上的「已复制」——反馈贴在动作上更准 |
| 需要人读完的短失败原因 | 必须人确认才能继续的对话框、设置页常驻错误条 |
| | 后台静默任务（如 `silent` 自动命名）——不要弹 |

判断句：这句话如果三秒后不必再盯着看，就用 Toast。这句话如果必须人点「确定」才算完，就不要用 Toast。

---

## 3. 核心原则

1. **全应用只有一套 Host**。`app/page.tsx` 里 `ToastProvider` + `ToastHost`。禁止再写第二套气泡、空下拉占位、菜单项变文案来顶替提示。
2. **调用只走 `useToast().showToast`**。不要 `alert`、不要在面板里画斜体空态充当消息。
3. **语气三种，不要自造第四种。**
   - `info`：说明「现在做不成」或「正在做」。
   - `success`：人刚点的操作完成了。
   - `error`：人刚点的操作失败了，可带服务端短句。
4. **控件文案保持动词。** 「生成标题」永远叫生成标题；成功与失败写在 Toast 里。
5. **没有内容就不要打开层。** 例如没有分支：Toast `i18n.noBranches`，不打开分支面板。判定与面板是否有内容必须同一套函数（现为 `sessionHasBranches`）。
6. **颜色跟主题走。** 用 `--bg-panel` / `--text` / `--border` / `--accent`，不要另起一套色。外形跟 Composer chip：`border-radius: 999px`，宽度随字，左侧圆点标语气。
7. **位置在文档区。** Host 锚 `data-toast-anchor`（文件列正文），顶部水平居中。文档列收起时才退回视口顶。不要再贴视口底。
8. **文案走 i18n。** 中英同一 key；句子短、不带 HTML。

---

## 4. 怎么做

```ts
const { showToast } = useToast();

showToast({ message: t("i18n.noBranches"), tone: "info" });
showToast({ message: t("title.updated"), tone: "success" });
showToast({ message: errorMessage || t("title.failed"), tone: "error" });
```

默认时长写在 `lib/toast.ts`，一般不要在调用处覆盖：

| 语气 | 停留 | 依据 |
|------|------|------|
| success | 4s | Sonner / 常见「完成了」默认 |
| info | 5s | Carbon Toast 默认；本仓还要从对话栏抬头看文档区 |
| error | 8s | 失败短句更长，留给人读完 |

Material 旧 Snackbar 的 1.5s / 2.75s 对本仓太短，不要学。同文案短时间去重，避免连点刷屏。

新增一类瞬时提示时：

1. 先问：这是动词控件的结果，还是一块需要打开的内容？
2. 是结果 → `showToast`；是内容（真有分支树、真有系统提示词）→ 打开原来的面板或页签。
3. 把句子做成 i18n key，不要在组件里写死中文。
4. 不要为了「看起来有反馈」而渲染空面板。

---

## 5. 为什么这样是对的

- **一种视觉语言**：人不用猜「这句话会出现在菜单里、下拉里，还是屏幕中间」。
- **控件保持可扫**：`⋯` 四项始终是完整历史 / 生成标题 / 分支 / 系统提示词。
- **失败可复述**：Toast 用 `aria-live`，错误语气更强，比藏在禁用按钮的 title 里容易看见。
- **和系统通知分工**：离开页面时的完成提醒仍用浏览器通知；人还在页里时用 Toast。

## 6. 检查清单

- [ ] 新反馈是否走 `showToast`，而不是空下拉 / 菜单改字 / `alert`
- [ ] 语气是否只落在 info / success / error 之一
- [ ] 触发控件的标签是否仍是动词
- [ ] 无内容时是否根本不打开层
- [ ] 文案是否走 i18n，样式是否只用现有 CSS 变量
- [ ] 静默后台路径是否故意不弹
