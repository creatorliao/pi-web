# 最佳实践_调查研究到方案确认再改代码

| 属性 | 值 |
|------|----|
| 日期 | 2026-08-19 |
| 适用 | 本仓（及同类产品仓）要改一块已有能力时：先查清再写方案，人确认后再动代码 |
| 落点 | `docs/02-Areas/` 长期做法；专题证据仍进 `docs/01-Projects/<主题夹>/` |
| 来源 | 本轮「对话标题自动化命名」实际走了一遍：理需求 → 读现状源码 → 查 GitHub 同行 → 出方案等确认 |

本文写人怎么做。交付物长什么样，以主题夹里的编号文件为准。

---

## 1. 什么情况下用

你准备改产品里一块已经存在的能力（或补一层默认行为），还没想清楚「现在到底怎么做的」「别人怎么做的」「我们改哪几处」。  
这时候不要直接开写。先把需求、现状、同行、方案四份东西落到同一个主题夹，等人看过再改代码。

不适用：改一个确定的错别字、补一条已有方案里写明的测试、用户已经 Gate-S 授权且范围没变。那种直接做，补一行进展即可。

---

## 2. 为什么先查再改

对话里的结论会过期，会话会分叉。主题夹才是下一轮能接着干的账本。

只看感觉改代码，常见翻车：

- 仓库里其实已经有生成器，你又写一套。
- 界面上「像有标题」其实只是截断展示，门控判错。
- 学了同行的表面（JSON 标题、每次都改名），把费用和覆盖用户名一起带进来。

先把事实写下来，方案才能指回文件和链接，确认时才有东西可驳。

---

## 3. 核心原则

1. **需求先成文**：目标、做什么、不做什么、成功标准，写成 `01-需求`。口述只作输入。
2. **现状用源码说话**：打开的文件、函数、API、有无自动触发，写进 `02-分析报告`。推测标清楚。
3. **同行用链接说话**：官方文档、Issue、PR、配置键，写进 `03-调查报告`。不要只写「业界都这样」。
4. **方案综合三份材料**：复用已有资产，只补缺口。默认选项写死，待决项单列。
5. **人确认后再改代码**：计划可以写完，施工必须等一句确认。智能体不得把「我写了方案」当成授权。
6. **一篇一事、同一主题一个夹**：需求、分析、调查、方案分文件；夹内序号接续；`00-README` 一行进度。

---

## 4. 怎么做（按顺序）

### 4.1 理清需求

把用户原话收成四块：Why、In Scope、Out of Scope、约束。  
含糊的写成 `@待确认`，给选项和推荐，不要假装已经拍板。

做完标志：夹里有 `01-需求_日期_主题.md`，别人只读这一份就知道成功长什么样。

### 4.2 理清现状（源码）

先列本仓相关符号再读，禁止凭记忆下结论。本轮实际用过的问法可以原样留着：

```text
auto-name / generateSessionTitle / setSessionName / appendSessionInfo
session.name / firstMessage / session_info / handleAutoName
```

对每个入口记一张表：谁调用、写到哪、算不算「已命名」。  
展示回退和持久化字段必须分开，否则后面门控会错。

做完标志：`02-分析报告` 有结论先行、功能地图、特性有无表、和需求对照的缺口表、文件路径。

### 4.3 查同行（含 GitHub）

按「同类产品 + 同一用户问题」搜，不要只搜品牌名。本轮有用的检索：

```text
Open WebUI title generation task model JSON
LibreChat titleConvo titleTiming immediate final
LobeChat summaryTopicTitle enableIntelligentTopicName
ChatGPT lock conversation title overwrite rename
```

每家只抓四件事：**默认开不开、何时触发、触发几次、人改的名会不会被盖掉**。再补技术合同：模型、上下文长度、解析失败怎么办。

一手来源优先：文档页、yaml 配置键、PR 说明、维护者在 Discussion 里的一句话。论坛抱怨当风险，不当规格。

做完标志：`03-调查报告` 有对照表和可点开的 URL。

### 4.4 综合出方案

对着缺口表写「改哪里、不改哪里」。优先接现成函数，不重造生成器。  
把同行做法分成：要对齐的（默认自动、空名才写、失败不假成功）和不要学的（反复改用户标题、解析失败写成第一句还算成功）。

做完标志：`04-方案` 含默认规格、门控、文件落点、验收清单、Gate-S 默认值。文首写明未确认不改代码。

### 4.5 人机校验，再执行

智能体交文档，人看需求是否说全、分析是否对得上仓库、方案是否越权。  
人回复确认或改待决项之后，才进入改代码、测试、留证据。  
没有这句确认，下一轮仍停在计划节拍。

---

## 5. 主题夹里要留下哪几份

一次「调查后优化」至少四份，外加索引：

| 序号 | 文件名模式 | 回答什么 | 可追溯到 |
|------|------------|----------|----------|
| 00 | `00-README.md` | 现在做到哪、下一闸 | 夹内文件表 + SSOT 一行 |
| 01 | `01-需求_日期_主题.md` | 要什么、不要什么 | 用户原话 / 本轮对话 |
| 02 | `02-分析报告_日期_….md` | 仓库现在怎么做 | 路径、符号、测试文件 |
| 03 | `03-调查报告_日期_….md` | 别人怎么做 | 文档与 GitHub URL |
| 04 | `04-方案_日期_….md` | 我们准备怎么改 | 回指 01～03 的条目 |

需要时再追加 `05-` 改善报告、施工记录。不要把需求和方案糊成一篇「聊天摘要」。

长期做法（本文这类）进 `docs/02-Areas/YYYYMMDD-xx-最佳实践_….md`，不要在 Areas 下再套主题夹。

---

## 6. 可追溯要满足什么

- **需求可追溯**：方案 F-0x / 门控能指回 01 的编号。
- **现状可追溯**：分析里的判断能打开具体文件，而不是「好像有个按钮」。
- **同行可追溯**：调查结论带 URL；改了日期或版本要在表头写明检索日。
- **决策可追溯**：待决项谁选了哪个，写在 README 或方案修订里，不要只留在对话。
- **实现可追溯**（确认后）：提交说明或 Handoff 写「按 04-方案 §x」，验收勾选留证据。

缺任何一环，下一轮只能重查。

---

## 7. 常见误区

| 误区 | 正确做法 |
|------|----------|
| 用户说了「分析一下」就开始改代码 | 分析报告和方案先落盘，等确认 |
| 界面上看见标题就当已命名 | 先查是 `name` 还是 `firstMessage` 截断 |
| 同行有 JSON 标题就改解析合同 | 先看本仓解析是否已覆盖；合同变更要写进方案 |
| 学 ChatGPT 持续改标题 | 用户已命名则停止自动 |
| 新的一天再开一个平行主题夹 | 同主题只追加序号 |
| 最佳实践和需求都堆进 Areas | 专题四件套进 `01-Projects`；Areas 只放长期做法 |
| 调查只有「我印象里」 | 补链接，或标明 `[推定]` |

---

## 8. 适用边界

**适用**：已有实现要优化；需求依赖「现在怎么做」和「别人怎么做」；需要人拍默认行为。

**不适用**：纯文档错字；已确认方案的收尾实现；与源码无关的纯制度讨论（那种直接写 Areas 一篇即可）。

**前提**：能读本仓源码；能访问 GitHub / 官方文档。内网断外网时，调查报告写明「仅源码 + 已知文档」，把同行表标为不完整。

## 9. 检查清单

- [ ] 已浏览 `docs/01-Projects/`，同主题是追加而不是新开夹
- [ ] `01-需求` 有目标、In/Out、约束、待决
- [ ] `02-分析` 结论能指到文件，展示名和持久化名已分开
- [ ] `03-调查` 至少两家一手来源，有对照表和 URL
- [ ] `04-方案` 写明复用什么、补什么、失败怎么办、验收怎么勾
- [ ] `00-README` 进度一行已更新
- [ ] 回复里写了「等确认、未改业务代码」（若仍在计划节拍）
- [ ] 未经确认没有改产品代码
