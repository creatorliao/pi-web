# 调查报告：pi-web 与本机 `pi` 的运行时关系

| 属性 | 值 |
|------|----|
| 编号 | `20260819-01` |
| 日期 | 2026-08-19 |
| 领域 | `docs/02-Areas`（本文件位于该目录根下，不另建子文件夹） |
| 问题 | 本机已安装 CLI `pi`，pi-web 发消息时是调用该可执行文件，还是自带内核 |
| 方法 | 读仓库依赖、启动脚本、`startRpcSession` 实现，并对照 SDK 包元数据 |
| 范围 | 本仓库 `@agegr/pi-web`（调查时 `package.json` 版本 `0.8.9`） |

## 1. 结论

**推荐判断：pi-web 不调用本机 PATH 上的 `pi` 二进制。对话内核嵌在 Next.js Node 进程里，来自 npm 包 `@earendil-works/pi-coding-agent`（及同族 `pi-agent-core` / `pi-ai`）。**

本机 `pi` 与 pi-web 是**同一内核家族的两种入口**：

| 入口 | 形态 | 内核加载方式 |
|------|------|----------------|
| `pi` | TUI / CLI | 全局或本地安装的 `@earendil-works/pi-coding-agent`，`bin.pi` 指向 `dist/cli.js` |
| `pi-web` | 浏览器 + Next.js | 把同一 SDK **import 进服务端**，`createAgentSessionFromServices()` 进程内建会话 |

二者默认共用 `~/.pi/agent/`（可用环境变量改目录），因此会话文件、模型、鉴权、技能在多数情况下互通。版本以各自安装的 SDK 为准；Web 侧当前钉死 `0.84.2`，与本机 `pi --version` 可能不一致。

> **注意：** Agent 工具（bash、git、npx 等）会在会话 `cwd` 下执行**本机操作系统命令**。那是工具层，不是「再拉起一个 `pi` 子进程」。

## 2. 调查问题拆解

需要分开回答的是三件事，不能混为一谈：

1. **对话内核从哪来？** 是否 `spawn("pi", …)`。
2. **用户数据存在哪？** 是否与 TUI 读同一棵目录。
3. **工具执行的是谁？** 谁在跑用户机器上的 shell / git。

## 3. 证据

### 3.1 启动脚本不拉起 `pi`

`bin/pi-web.js` 只做两件事：检查 Node 版本，然后用当前 Node 启动 Next：

```text
spawn(process.execPath, [nextBin, "start", …])
```

子进程是 `next`，不是 `pi`。开发态 `npm run dev` 同样只起 Next（默认端口 `30141`）。

全仓库检索：没有 `spawn` / `execFile` 以 `pi` 为可执行文件名的调用。`child_process` 出现在 worktree、npx、git、导出 HTML 等辅助路径，与 Agent 主循环无关。

### 3.2 发消息时在进程内创建 AgentSession

`AGENTS.md` 与 `lib/rpc-manager.ts` 一致：

```text
浏览器 POST /api/agent/[id]
  → startRpcSession()
  → createAgentSessionServices()
  → createAgentSessionFromServices()
  → 内存中的 AgentSession.prompt() / subscribe()
  → SSE GET /api/agent/[id]/events 回推事件
```

关键 import：

```ts
import {
  createAgentSessionFromServices,
  createAgentSessionServices,
  getAgentDir,
  SessionManager,
  SettingsManager,
} from "@earendil-works/pi-coding-agent";
```

只读浏览会话（列表、按 id 读、按 leaf 取上下文）走 `lib/session-reader.ts` 的 `SessionManager`，**不创建** `AgentSession`。只有真正发送 / 需要交互运行时才 `startRpcSession()`。

同一 session id 的 wrapper 放在 `globalThis.__piSessions`，闲置约 10 分钟回收。这是进程内注册表，不是外部 CLI 进程表。

### 3.3 依赖即内核，且该包自己就是 `pi`

本仓库 `package.json` 钉死：

- `@earendil-works/pi-coding-agent` `0.84.2`
- `@earendil-works/pi-agent-core` `0.84.2`
- `@earendil-works/pi-ai` `0.84.2`
- `@earendil-works/pi-tui` `0.84.2`

该 coding-agent 包的 `package.json` 声明：

```json
"bin": { "pi": "dist/cli.js" }
```

因此本机命令 `pi` 通常就是**这个包的 CLI 入口**；pi-web 用的是同一包的 **library 入口**（`createAgentSession*`），不是再去 PATH 里找 `pi`。

`pi-web` 还 import 了 `pi-tui` 的键位等能力，用于无头自定义 UI，进一步说明它嵌入的是 SDK，而不是外壳脚本。

### 3.4 配置目录与 TUI 对齐

SDK `getAgentDir()`：

1. 若设置了 Agent 目录环境变量，则用该路径（支持 `~`）。
2. 否则为 `{homedir}/.pi/agent`。

会话落在 `~/.pi/agent/sessions/<encoded-cwd>/<timestamp>_<uuid>.jsonl`。Web 与 TUI 默认读写同一树。

### 3.5 工具层会碰本机命令，但不是 `pi`

| 路径 | 作用 |
|------|------|
| SDK 内建 coding tools（bash / read / edit / write 等） | 在会话 cwd 执行本机能力 |
| `lib/project-command-env.ts` | 项目命令 / bash 扩展的执行封装 |
| `lib/npx.ts`、`lib/worktree.ts`、`lib/git-changes.ts` | npx、git worktree、变更查询 |

`rpc-manager.ts` 明确：不要把工具 allow-list 收成「仅内建 coding 名」，否则扩展工具会从 Web 会话消失，而 `pi` CLI 仍保留。设计目标是 **Web 与 CLI 看到同一套工具注册表**，实现方式仍是进程内 SDK，不是转发到 CLI。

## 4. 运行时对照

```text
┌─────────────┐     HTTP / SSE      ┌──────────────────────────┐
│  浏览器 UI  │ ◀─────────────────▶ │  Next.js（pi-web 服务）   │
└─────────────┘                     │  import pi-coding-agent   │
                                    │  AgentSession（同进程）    │
                                    └────────────┬─────────────┘
                                                 │ 读写
                                                 ▼
                                    ~/.pi/agent/  （会话 / 设置 / 鉴权 / 技能）
                                                 ▲
                                                 │ 读写
┌─────────────┐                     ┌────────────┴─────────────┐
│  终端里的 pi │ ── dist/cli.js ──▶ │  同一 SDK（可能另一版本） │
└─────────────┘                     └──────────────────────────┘

没有：pi-web ──spawn──▶ 本机 pi
有：  工具 bash/git/npx ──exec──▶ 本机 OS
```

## 5. 对使用与排障的含义

1. **没装全局 `pi` 也能跑 Web**：只要 `node_modules` 里 SDK 完整。
2. **装了 `pi` 也不会被 Web 自动调用**：PATH 里的二进制与 Web 进程无父子关系。
3. **会话能在两边看到**：因为默认同一 `~/.pi/agent/sessions/`。
4. **行为分叉优先查版本**：`pi --version` 与 `node_modules/@earendil-works/pi-coding-agent/package.json` 的 `0.84.2` 是否一致。文件格式大体兼容，扩展、工具过滤、压缩事件名等细节可能不同。
5. **改环境变量改的是两边的数据根**：若只改 Web 进程的 Agent 目录，TUI 仍读默认路径，会话会「消失」。
6. **CPU / 网络占用在 Node 服务进程**：一次对话不会额外出现名为 `pi` 的 Agent 子进程；模型请求由进程内 SDK 发出。

## 6. 明确不在本次结论内的事项

- 未在本机实测 `pi --version` 与当前 lockfile 是否同号。
- 未追踪 SDK 内部是否在极少数路径（例如某些导出、二进制资源）再 spawn 自身 CLI；就 pi-web 仓库调用面而言，主路径均为 library API。
- 未覆盖远端部署（另一台机器上的 pi-web）与开发者笔记本上 `pi` 的数据隔离——那是部署拓扑问题，不是「内核不内核」。
