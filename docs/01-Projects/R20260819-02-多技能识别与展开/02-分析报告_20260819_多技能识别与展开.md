## 1. 结论先说

| 问题 | 结论 |
|------|------|
| 第一颗为什么能下拉看描述 | 发送时 SDK 把行首 `/skill:name` **整份 SKILL.md** 折成 `<skill>…</skill>` 写进 user 消息；气泡层用正则还原成一颗芯片，下拉渲染这份信封 |
| 第二颗为什么是纯文本 | 同一套正则和同一套 SDK **只认一个信封 / 只展开行首一颗**；第二颗被当作第一颗后面的 `args` |
| 智能体是否真触发了两颗 | **没有。** 正式注入的只有第一颗。第二颗最多以命令字符串出现；若该技能休眠（禁止模型自行调用），模型几乎拿不到说明书 |

输入框里两颗都变色，只说明 **Composer 分词成功**，不能推出 **Agent 双展开成功**。

## 2. 三层链路

```text
输入框分词（多颗）     →  原样发送 "/skill:a /skill:b 提问"
        │
        ▼
SDK _expandSkillCommand（只认行首一颗）
        │
        ▼
落盘 / 模型上下文：  <skill a>全文</skill>  +  "/skill:b 提问"
        │
        ▼
气泡 skillExpansionToCommand（只还原一颗芯片）
        │
        ▼
画面：芯片 a ▾   +   纯文本 "/skill:b 提问"
```

三层各自独立。R20260819-01 只修了第一层。

## 3. 第一颗为什么能下拉

### 3.1 发送时变成信封

`@earendil-works/pi-coding-agent` `AgentSession._expandSkillCommand`（`dist/core/agent-session.js`）：

```text
若 text 不是以 "/skill:" 开头 → 原样返回
否则：
  name = 第一个空格前的技能名
  args = 第一个空格后的全部内容（trim）
  读 skill.filePath，去掉 frontmatter
  得到：
    <skill name="…" location="…">
    References are relative to ….

    {SKILL.md 正文}
    </skill>

    {args}          ← 可选
```

`prompt` / `steer` / `followUp` 都会走这步。展开后的字符串写入 **user 消息**，也就是会话里看到的「已发送」原文。

因此第一颗能下拉：下拉看的不是前端另查的简介，而是 **已经写进消息的整份技能正文**。

### 3.2 气泡只画一颗芯片

`lib/slash-display.ts` 的 `SKILL_EXPANSION_RE`：

- 锚定整段：`^<skill …>…</skill>(?:\n\n参数)?$`
- 只捕获 **一个** `name` 和 **一段** 可选 `args`
- `skillExpansionToCommand` 还原成 `` `/skill:${name} ${args}` ``

`MessageView` `UserMessageView`：

- `commandName` = 第一个空白前（即 `/skill:第一颗`）
- `commandArgs` = 其余全部（含第二颗 `/skill:` 和用户提问）
- 只有 `commandName` 是带箭头的 `<button>`；`commandArgs` 是普通 `<span>`
- `expanded === true` 时用 Markdown 渲染 **整段 `content`**（第一颗信封 + 后面的字）

这与截图一致：第一颗可下拉，第二颗是后面那截纯文本。

侧栏会话标题同样走 `skillExpansionToCommand`，多技能时标题也会只露出第一颗命令。

## 4. 第二颗及更多颗为什么失效

对示例：

```text
/skill:c01-course-topic-select /skill:character-encoding-scanner 这两个技能怎么用
```

SDK 解析结果：

| 字段 | 值 |
|------|----|
| skillName | `c01-course-topic-select` |
| args | `/skill:character-encoding-scanner 这两个技能怎么用` |
| 读盘 | 只读第一颗的 `SKILL.md` |
| 第二颗 | **不查找、不读文件、不包信封** |

`formatSkillInvocation`（`pi-agent-core`）同样是「一颗技能 + 可选附加说明」，没有多信封 API。

`composer-tokens.ts` 已能把两颗都标成 `kind: "skill"`（测试用例「colors multiple skills…」），注释写明：**只做展示与芯片删除，不改发送给 pi 的原文契约。** 所以输入层「认得」和运行层「展开」是两回事。

## 5. 智能体「识别并运作」的真实含义

技能进模型有两条路：

| 路径 | 谁触发 | 内容 | 休眠技能（`disable-model-invocation`） |
|------|--------|------|----------------------------------------|
| A. 显式 `/skill:name` | `_expandSkillCommand` | 整份 SKILL.md 进 **本条 user** | 必须靠这条，系统提示里 **没有** 该技能条目 |
| B. 系统提示清单 | `formatSkillsForPrompt` | 仅 name / description / location，并指示模型 **用 read 再读文件** | **被排除**，模型默认不知道它 |

因此：

- 第二颗若是普通可见技能：模型可能在系统提示里看到简介，自行 `read` 文件。这是 **模型自觉**，不是运行时保证。
- 第二颗若是休眠技能（大量课程/工具技能如此）：**没有路径 A 就等于没触发。**
- 即便模型看见 `/skill:foo` 字样，也不等于说明书已注入；用户担心「只识别一个」在机制上成立。

「运作」在本仓库应定义为：**该技能信封出现在本轮 user 上下文中**。不要用「模型回了两段话」当验收。

## 6. 根因

不是 Markdown 漏画，也不是输入框只分出一颗 token。

根因是 **展开与还原都按「整段话 = 一颗斜杠命令」设计**：

1. SDK：`startsWith("/skill:")` + **第一个空格** 切 name/args。
2. 展示：`^…$</skill>` 只还原一颗芯片。

R20260819-01 把输入改成「一句里多颗」，发送/气泡仍停在旧契约。这是前后链路不一致，不是偶发渲染 bug。

## 7. 影响面

| 位置 | 影响 |
|------|------|
| `pi-coding-agent` `_expandSkillCommand` | 真正少注入的技能正文 |
| `lib/slash-display.ts` | 多信封无法还原；或单信封 + 尾巴里还有 `/skill:` |
| `components/MessageView.tsx` | 只渲染一颗下拉 |
| `components/SessionSidebar.tsx` | 会话名只带第一颗 |
| `composer-tokens.ts` | 无发送副作用；可复用其分词规则 |
