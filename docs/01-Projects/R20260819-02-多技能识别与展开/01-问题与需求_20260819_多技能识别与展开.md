## 1. 问题（As-Is）

用户在同一条消息里连续写入两颗技能后再提问，例如：

```text
/skill:c01-course-topic-select /skill:character-encoding-scanner 这两个技能怎么用
```

手验现象：

| # | 现象 | 严重度 |
|---|------|--------|
| P-01 | 第一颗 `/skill:…` 渲染成可点击芯片，下拉可看到技能正文（描述/说明书） | 能力正确，应保留 |
| P-02 | 同一气泡里的第二颗仍是普通字，没有芯片、没有下拉、看不到描述 | 展示缺口 |
| P-03 | 用户担心：界面上有两颗技能，运行时可能只正式触发第一颗 | 机制风险（分析后已证实） |

P-01 是期望能力。P-02 / P-03 是本主题要解决的问题。

## 2. 需求（To-Be）

### 2.1 业务目标

一条用户话里可以同时点名多颗技能。每一颗都要：

1. **被识别**（不是漏检成普通斜杠字）；
2. **可下拉**（与第一颗同级的芯片 + 描述/正文）；
3. **对智能体生效**（对应 `SKILL.md` 进入本轮上下文，而不是只留下命令名）。

### 2.2 功能需求

| # | 需求描述 | 优先级 | 来源 |
|---|----------|--------|------|
| F-11 | 已发送用户气泡中，每个完整 `/skill:name` 都画成与第一颗同类的下拉芯片 | 必做 | 用户 |
| F-12 | 点击任一芯片的下拉，展示该技能的描述及相关正文（与现网第一颗「展开看 `<skill>` 信封」同级） | 必做 | 用户 |
| F-13 | 芯片后的普通说明（如「这两个技能怎么用」）仍作为正文，不并进某一颗技能名 | 必做 | 用户截图 |
| F-14 | 发送路径对消息里每一颗可解析的 `/skill:name` 做正式展开；未知技能名保持原文透传 | 必做 | 用户对「真正触发」的担心 |
| F-15 | 三颗及以上与两颗同一套规则，不单独写死「最多两颗」 | 必做 | 用户「将来更多」 |
| F-16 | 输入框多颗着色（F-03d）保持；本主题不回退芯片条 | 必做 | R20260819-01 |

### 2.3 非功能

- 展示层不得伪造「已展开」：芯片能下拉，不等于模型一定读到正文；F-14 必须与 F-11 对齐。
- 会话落盘仍保存展开后的用户消息（与现网「信封进 session」一致），避免刷新后丢正文。
- 不改技能目录扫描规则；复用已加载的 `Skill` 列表（name / filePath / description）。
- 中文 IME、发送契约「用户看见的是 `/skill:` 混排字」在输入框侧不变。

### 2.4 非目标

- 不在本主题改技能安装、休眠开关 UI。
- 不要求模型必须并行「执行」两套互斥流程；生效指 **说明书进上下文**。
- 不强制立刻给上游 `pi-coding-agent` 提 PR；可先在 pi-web 侧补齐，再视需要回馈上游。

## 3. 成功标准（检查表）

1. 一条消息含 2 颗及以上 `/skill:` 时，气泡里芯片数量等于可解析技能令牌数。
2. 每一颗芯片下拉内容对应该技能文件，而不是把后面技能名当第一颗的参数。
3. 打开该轮落盘的 user 文本（或调试展开结果）：出现与令牌数相同的 `<skill name="…">` 信封；剩余自然语言在信封之后。
4. 对 `disable-model-invocation: true` 的技能，不展开则模型看不到说明书；展开后必须能看到。
5. 仅一颗技能且后接参数的旧消息，展示与现网兼容（一颗芯片 + 参数）。
