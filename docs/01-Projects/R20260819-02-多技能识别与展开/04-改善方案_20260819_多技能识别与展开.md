## 2. 推荐设计（路线 C）

### 2.1 展开（F-14 / F-15）

新增 `lib/skill-expand.ts`（名称可微调），职责：

1. 用与 `parseClosedComposerTokens` 相同的闭合 `/skill:name` 规则，从左到右找出全部 skill 令牌。
2. 对每个令牌：在已加载 Skill 列表中按 **精确 name** 查找；找到则读文件、`stripFrontmatter`、生成与 SDK **字节级同构** 的信封（字段顺序、换行、`References are relative to` 与现网一致，保证旧 `SKILL_EXPANSION_RE` 对「仅一颗」仍成立）。
3. 拼接：`信封1 + \n\n + 信封2 + … + \n\n + 剩余散文`。
4. 剩余散文 = 原文去掉已展开令牌及其后多余空格（复用 `removeComposerToken` 的空白规则），保留用户提问。
5. 未知 `/skill:foo`：不删令牌，留在散文里。
6. 若一个 skill 令牌都没有：返回原文（含行首不是 `/skill:` 但中间有技能的情况——此时仍应展开中间那些令牌）。

调用点：`lib/rpc-manager.ts`（及任何直接 `prompt` / `steer` / `followUp` 的入口）在把用户字交给 inner agent **之前**执行。这样：

- SDK 再跑 `_expandSkillCommand` 时，文本已以 `<skill` 开头，**不会** `startsWith("/skill:")`，不会把第二颗吃进 args。
- 若因时序未预展开、仍以 `/skill:` 开头，SDK 的单颗展开仍是安全兜底。

技能列表来源：与 slash 面板相同的资源加载结果（session 已有的 skills），避免再扫盘两套规则。

### 2.2 还原与气泡（F-11 / F-12 / F-13）

扩展 `lib/slash-display.ts`：

- 保留 `skillExpansionToCommand`（单信封，侧栏/旧测试继续用）。
- 新增 `parseSkillExpansions(text)`：循环切完整信封列表 + 尾部散文。
- 信封识别条件与现网一致（opening、`References are relative to`、闭合 `</skill>`），避免把用户手打的残缺标签误折叠。

`UserMessageView`：

- 若解析出 ≥1 个信封：对每个信封画一颗芯片按钮；`expandedId` 用 name+index（允许两颗同名）。
- 下拉只渲染 **该信封全文**（或信封 body），不要整段消息。
- 尾部散文单独成段，样式同现在的 `commandArgs`。
- 零信封：走现有 Markdown 路径。

### 2.3 侧栏（P1）

`session-title` / `SessionSidebar`：多信封时标题用 `/skill:A` 或 `/skill:A +2`，不要把第二颗命令和提问糊成 50 字垃圾标题。
