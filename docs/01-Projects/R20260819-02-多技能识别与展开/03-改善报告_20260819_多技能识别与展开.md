## 1. 目标态

用户发送：

```text
/skill:A /skill:B 这两个技能怎么用
```

之后应同时满足：

| 层 | 目标 |
|----|------|
| 气泡 | 两颗可下拉芯片（A、B）+ 正文「这两个技能怎么用」 |
| 落盘 / 模型 | 两个完整 `<skill>` 信封，顺序与输入一致，提问接在全部信封之后 |
| 输入框 | 维持现网多颗着色，不回退顶栏芯片条 |

一颗技能 + 参数的旧会话继续：一颗芯片 + 参数文本 + 下拉看该信封。

## 2. 缺口对照

| 需求 | 现状 | 缺口 |
|------|------|------|
| F-11 多芯片 | 仅第一颗是按钮 | 展示要按令牌拆芯片 |
| F-12 各下拉各正文 | 下拉整段 `content`（主要是第一颗信封） | 每颗芯片绑定自己的信封或本地 SKILL.md |
| F-13 提问独立 | 提问混在 `commandArgs` 里，与第二颗命令糊在一起 | 令牌与散文分离 |
| F-14 全部正式展开 | SDK 只展开行首一颗 | 发送前或 SDK 内循环展开 |
| F-15 N 颗 | 无上限分词，但展开/还原写死 1 | 展开与还原都改成列表 |
| F-16 输入不变 | 已满足 | 回归即可 |

只修气泡、不修展开：用户点得开描述（若前端另读文件），模型仍可能只用第一颗。改善报告认定 **F-14 与 F-11 必须同批交付**，否则再次制造「看见两颗、只生效一颗」。

## 3. 改善优先级

1. **P0 运行时多展开**：保证智能体上下文与用户点名的技能集合一致。
2. **P0 气泡多芯片**：与 P0 展开结果对齐；旧单信封消息兼容。
3. **P1 侧栏标题**：多技能时不要只显示第一颗命令（可截断为 `/skill:A +N`）。
4. **P2 上游回馈**：把循环展开贡献回 `pi-coding-agent`，避免 CLI 与 Web 行为分叉。

## 4. 风险

| 风险 | 说明 | 处理 |
|------|------|------|
| 上下文膨胀 | N 份 SKILL.md 一次性注入 | 先如实展开；后续再做折叠/引用。在方案里写明上限提示（可选） |
| 技能正文含 `</skill>` 样例 | 现网单信封已用贪心闭包 | 多信封按「从左扫描完整信封」解析，不整段一条正则吃到底 |
| 只改展示去读盘 | 刷新后描述在，模型仍缺正文 | 禁止「只做 UI」作为本主题完成态 |
| 与 CLI 不一致 | 同一 session 在 CLI 打开仍只展开一颗 | 优先在 **prompt 入口之前** 展开，使落盘对 CLI 也是多信封 |

## 5. 验收口径（改善是否完成）

与需求成功标准一致，补三条回归：

- 无 `/skill:` 的普通用户句，气泡仍走 Markdown，不出现空芯片。
- 行首不是 `/skill:`、中间才出现 `/skill:`：按方案「全文扫描令牌」展开（见 04），不得因 `startsWith` 整句跳过。
- 未知 `/skill:not-exist`：保持原文，不制造空信封。
