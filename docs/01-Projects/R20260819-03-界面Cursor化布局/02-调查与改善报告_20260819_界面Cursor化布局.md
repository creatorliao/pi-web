# 调查与改善报告：界面元素与排布

| 属性 | 值 |
|------|----|
| 日期 | 2026-08-19 |
| 方法 | 读 `AppShell` / `SessionSidebar` / `SettingsDialog` / `ChatInput`；对照 Cursor 社区 2025–2026 布局讨论与通用 AI 三栏惯例 |
| 范围 | 壳层信息架构与主界面元素；不含模型调用与会话存储 |

## 1. 结论先说

当前 pi-web 是 **「左：项目+会话+文件 · 中：对话 · 右：文件预览」**。  
Cursor 重度用户要的编辑器窗口是 **「左：文件 · 中：编辑/审阅 · 右：智能体（历史+过程+输入）」**。

中间栏被对话占满、文件被挤到最右，是**肌肉记忆冲突的根因**，不是配色问题。  
程序员向元素（路径、uuid、token、系统提示、构建目录）叠在主路径上，会让普通用户觉得这是「开发者控制台」。

改善应分两层，不要混成一次「大改皮肤」：

1. **骨架对调**（本 R 主价值）：三栏角色与 Cursor 编辑器窗口对齐。
2. **信息下沉**：主界面只留任务控件；诊断项进设置 / 高级。

增量诉求（「中间输入」人群）的论证与代价见 **§9**。结论：可以兼容，但只建议做「对话块整体换槽」，不要做两套导航。

## 2. 现状：三栏各自在干什么

依据 `components/AppShell.tsx` 注释与结构（约 1697–2197 行）：

| 栏 | 现状角色 | 主要组件 |
|----|----------|----------|
| 左 | 品牌标题、新建会话、刷新会话、项目/cwd 选择、worktree、**会话树**、折叠的**文件树**、底栏设置 | `SessionSidebar` + `FileExplorer` |
| 中 | 顶栏（侧栏开关、会话工具、统计、打开文件）、**整栏 ChatWindow** | `ChatWindow` / `ChatInput` |
| 右 | 仅在打开文件时出现：`TabBar` + `FileViewer`，按钮文案是「文件面板」 | 文件预览，不是对话 |

这与用户截图、以及用户口述习惯**左右对调了「对话」和「文件」**。

左侧还把「对话历史」和「目录树」叠在同一栏：先会话、后文件。Cursor 编辑器窗口则把目录留给左栏，把对话历史放进右侧 Agents 栏。

## 3. 对照：Cursor 实际有两套壳（本项目只对齐一套）

公开讨论（Cursor Forum 2025–2026）里，Cursor 3 至少有：

| 模式 | 常见排布 | 是否对齐本需求 |
|------|----------|----------------|
| **编辑器窗口（Editor Window）** | 主侧栏文件在左，编辑器居中，Agent/Chat 在右 | **对齐。用户明确要这个。** |
| **Agents / Glass 窗口** | 智能体为中心，文件位置常被换边或收起 | 不作为默认；难复刻且用户说不必仿独有壳 |

社区反复出现的诉求是：文件在左、AI 在右——说明这是 IDE 用户的默认心理模型，不是个人癖好。

**不复刻清单（Cursor 独有 / 难仿 / 用户不需要）**

- Glass 与编辑器双窗口、启动默认 Agents
- 底栏 Git 分支、问题数、Cursor Tab / Agent Stats
- 命令面板作为找功能的主路径
- 终端、扩展、多窗口同步

**值得对齐的习惯（低成本、高肌肉记忆）**

- 左文件、中标签页、右对话
- 右侧栏顶上「新建」
- 当前线程的过程就在输入框上方滚
- 历史在同一右侧栏里切，而不是跑到左边另找一棵「session 树」
- 打开文件 = 中间加 Tab，而不是再开一扇「侧预览」当主阅读区

## 4. 对照：通用消费级 AI（用来决定「什么进设置」）

ChatGPT / Claude / 部分 Notion AI 的常见三栏是：

```text
左：历史导航    中：对话    右：产物/画布（有才展开）
```

这与 **Cursor 编辑器窗口** 不同：消费级把「对话」当主舞台；IDE 把「文件」当主舞台。

本产品若同时服务「普通大众」和「Cursor 重度用户」，正确拆法是：

- **空间模型跟 Cursor 编辑器**（用户已拍板）。
- **信息密度跟消费级**：左栏像「我的资料」，不要像资源管理器调试台；右栏像「助手」，不要像 RPC 控制台。

Jakob 定律：熟布局降低认知负担。用户已经有一套 Cursor 熟布局，再叠一套 ChatGPT 中置对话，会两头不讨好。

## 5. 元素盘点：主界面留下 vs 下沉设置

分级：

- **P0 主路径**：做任务每天都要点。
- **P1 任务中偶发**：做的时候要看见，平时可收。
- **P2 诊断/工程**：给排查用，默认进设置或「高级」。

### 5.1 建议留在主界面（P0 / 少量 P1）

| 元素 | 现状 | 建议位置 | 说明 |
|------|------|----------|------|
| 项目切换 | 左栏 cwd 下拉，等宽路径 | 左栏顶，**显示文件夹名** | 大众认「这个项目」，不认盘符 |
| 目录树 | 左栏下半，与会话抢高 | **左栏主体** | 用户点名的目录树 |
| 新建对话 | 左栏「新建会话」，无 cwd 禁用 | **右栏顶 +** | 对齐 New Agent |
| 对话列表 | 左栏 session 树（含 Fork 父子） | **右栏**（列表或抽屉） | 用户点名历史在右 |
| 当前对话 + 输入 | 整个中栏 | **右栏下半** | 过程与输入在一起 |
| 文件标签 + 正文 | 右栏 | **中栏** | 审查文档的主舞台 |
| 模型选择 | 输入框 | 仍放输入框（Cursor 也在 Composer） | 换模型是任务动作 |
| 发送 / 停止 | 输入框 | 保持 | 已在 R01 对齐 |
| `@` / `/` 技能 | 输入框 | 保持 | 已在 R01 |
| 权限/工具强度 | 输入框工具预设 | 保留简名（如「只读 / 默认可改」），细则进设置 | 大众要懂「会不会改我的文件」 |
| 思考深度 | 输入框 thinking | 可留一档简控；`xhigh` 等词可进高级 | Cursor 也在输入区 |

### 5.2 建议移入设置或「⋯ 更多」（P2 为主）

| 元素 | 现状 | 建议 | 为何偏程序员 |
|------|------|------|----------------|
| 会话文件路径、session id、复制 | 顶栏统计气泡 | 设置 → 高级 → 当前对话 | uuid / jsonl 是排障 |
| Token / cache / 费用 / 命中率 | 同一气泡，等宽字体 | 设置 → 用量；或右栏「用量」折叠 | 运维仪表 |
| 系统提示全文 | 顶栏「系统」 | 设置 → 高级 | 开发者调试 |
| 「完整历史」按钮 | 顶栏 / 会话菜单 | 右栏历史即主历史；全量导出留设置 | 重复入口 |
| 「生成标题」 | 顶栏 | 自动命名后台做；失败再提示 | 不该占主条 |
| 会话内分支导航 | 顶栏 BranchNavigator | 右栏「版本/分支」折叠；或消息上的 Continue | pi 独有，保留但不顶栏示众 |
| 手动刷新会话列表 | 左栏刷新按钮 | 去掉或进高级；列表应自动更新 | 像运维控制台 |
| worktree / 打开仓库根 | 左栏 | 设置 → 项目 / Git | 普通用户无此概念 |
| Plugins 包管理 | 已在设置 | 保持；可标「扩展（高级）」 | 工程向 |
| Models.json / 发现上游模型 | 已在设置 | 保持在模型页，主界面不出现原始 id 堆叠 | 已相对合理 |
| 显示 `.next` / `node_modules` / 点文件 | 文件树默认全量（用户截图） | 默认隐藏；设置「显示隐藏文件」 | 最强的「这是给程序员的」信号 |
| 底栏式诊断（若后续有） | — | 不要做 Cursor 底栏仿品 | 用户已反感 |

### 5.3 已在设置、建议只改分层不搬家

现有 `SettingsDialog` 分栏：外观 / 模型 / 技能 / 插件。  
建议增补而不是打散：

```text
外观与布局
模型
技能
项目（隐藏文件、工作目录说明）
高级（插件、用量、系统提示、会话文件、Git/worktree）
```

「功能透明」仍然满足：能找得到，只是不站在门口。

## 6. 关键旅程对照（用起来舒不舒服）

| 旅程 | 现在 | Cursor 习惯 | 目标 |
|------|------|-------------|------|
| 打开一个文档看 | 点左下文件树 → 文件出现在**最右**，对话仍占中间 | 文件在中间 Tab | 中栏打开 |
| 跟助手说话 | 眼睛在中间大栏 | 眼睛在右边栏，余光看中间 diff/文档 | 右栏对话 |
| 找上次对话 | 在**左边**会话树里翻，还可能和 Fork 父子缠在一起 | 右侧 Agents 列表 / 历史 | 右栏列表 |
| 新开一轮 | 左上「新建会话」，还要先有项目 | 右侧 New Agent | 右栏 + ，项目沿用当前左栏 |
| 看智能体改了什么 | 聊天气泡 + 可选打开右预览 | 中间看文件，右边看过程 | 中文件 + 右过程 |

## 7. 风险与边界

| 风险 | 说明 | 对策 |
|------|------|------|
| 消费级用户更熟「中间对话」 | 与 ChatGPT 默认不同 | 默认仍用编辑器骨架；设置提供助手布局（对话块居中）。见 §9 |
| 右栏又要历史又要长对话，会挤 | Cursor 也挤 | 历史用窄列表/可折叠；默认看当前线程 |
| 大改 `AppShell` 易回归 | 三栏是根布局 | 先只换栏角色，文案与隐藏项可同 PR 小步 |
| 与 R01 输入框抢文件 | `ChatInput` 已复杂 | 本 R 尽量只动壳，少动 Composer 内部 |

## 8. 改善优先级（供方案引用）

1. **换骨架**（F-01～F-04）：没有这一步，其它文案优化都治不好「别扭」。
2. **藏诊断**（F-05、F-07）：顶栏立刻干净。
3. **目录树降噪**（F-06）：普通人一眼看到「我的文档」而不是 `.next`。
4. **文案与设置分层**（F-08、F-09）；若批双布局，设置项与 F-11 一起做。
5. **独有能力降噪**（F-10）：能力还在，入口变矮。

## 9. 增量：两种 UI 能否同时兼容（代价）

### 9.1 两种熟布局分别是什么

| 称呼 | 谁熟 | 眼睛和手 |
|------|------|----------|
| **编辑器布局** | Cursor / VS Code 重度用户 | 左找文件，中审文档，右跟助手说话（输入在右下） |
| **助手布局** | ChatGPT / Claude 网页用户 | 中栏才是「说话的地方」，文件是旁边的产物 |

你不是「特殊到不该被服务」，只是产品发起人站在编辑器一侧。中间输入是**另一条大众路径**，不是错的。

### 9.2 代码上现在有多「写死」

`AppShell`（约 2200 行）把中栏注释为 `Center: chat`，右栏 id 为 `file-panel`。  
`lib/panel-layout.ts` 算最大宽度时，预留的是「对话最小宽度」，右侧才是可开关面板。  
`globals.css` 的 `.right-panel-*` 只服务「右边那一栏可收起」。

所以现状其实已经是**助手布局的亲戚**（对话居中、文件在右），只是左栏还叠了会话树。  
要兼容两种 UI，本质是：抽出「对话块 / 文件块」两个槽位，再按偏好对调——不是从零画两套界面。

### 9.3 三档做法与代价

| 档 | 做什么 | 相对「只做编辑器骨架」的增量 | 用户感知 |
|----|--------|------------------------------|----------|
| **A 单骨架** | 只换成编辑器布局 | 基准（约 1 个工作包量级的壳改） | 中间输入的人会别扭 |
| **B 槽位切换（推荐）** | 左栏始终是项目+目录；**对话块（历史+过程+输入）整体**与**文件工作区**对调；设置一项、写入 localStorage | 大约 **+30%～50%**（设置项、偏好持久化、宽度约束改成「主栏/辅栏」而不是「聊天/文件」）。回归面增加，但组件仍是一份 | 中间想打字的人切到「助手」；你保持「编辑器」 |
| **C 两套信息架构** | 助手模式再把历史搬回左栏（仿 ChatGPT），编辑器模式历史在右；新建按钮、空态、快捷键各写一套 | 大约 **+1.5～2 个工作包**，之后每个壳层功能要测两次。`SessionSidebar` 无法一次拆清 | 更像两个产品，维护会痛 |

**C 档代价过大**，本 R 不建议做。它要同时满足「历史永远在左」和「历史永远在右」，左栏职责会分裂。

**B 档可接受**：助手模式下，历史跟对话一起在中间（顶上可折列表），不是 ChatGPT 那样钉在最左。对「我只想在中间打字」已经够；对「历史必须在左」的人仍有一点差距——应在方案里写明，避免超卖。

### 9.4 会不会把人搞迷糊

设置里两个清晰名字即可，不要做实时预览拖拽或第三种 Glass：

- 编辑器：中间看文件，右边对话
- 助手：中间对话，右边文件

默认 **编辑器**（尊重发起人与本 R 原目标）。切换立即生效并记住。手机继续单栏抽屉，不跟桌面双布局绑死。
