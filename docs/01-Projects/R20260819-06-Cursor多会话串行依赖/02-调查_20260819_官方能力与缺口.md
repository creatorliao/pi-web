# 调查：Cursor 官方能否让多对话按依赖串行

**调查日**：2026-08-19  
**依据**：Cursor 官方文档（Agents Window、Multi-agent、Worktrees、Cloud Agent API、Automations、Hooks）及论坛对编排的讨论。产品迭代快，结论以文档语义为准，不保证下个版本不变。

---

## 根因（为什么你会觉得「只能守着」）

### 表层现象

多个 Composer / Agents 侧栏会话可以同时开、同时跑。官方主叙事是 **并行**（Worktree 隔离、Cloud 并行、`/multitask`），没有「会话队列」。

### 直接原因

本地聊天的生命周期是 **人点发送才开始**。没有「会话 B 订阅会话 A 的 stop」这一产品对象。A 跑完不会自动创建或唤醒另一个**独立聊天**。

### 根本原因

产品把「多 Agent」做成 **并发吞吐 + 隔离工作区**，把「先后顺序」放在：

- **同一计划里的依赖步骤**（计划内排序），或
- **仓库/外部事件**（PR 合并、CI、Webhook 再拉起**新的云端 Agent**），

而不是「IDE 里聊天对象之间的 DAG」。

### 修复方向

用官方已有的「计划依赖 / 子 Agent 编排 / 云端 Run 排队 / 自动化事件链」逼近需求；缺口用 API 或极薄脚本补，而不是等一个尚未存在的「聊天串行器」。

### 是否临时缓解

否。下面方案都是可长期用的官方或官方可编程面，不是绕过安全策略的黑科技。

## 官方能力对照（对你的三条需求）

| 官方能力 | 不同上下文 | 串行门禁 | 不值守 | 说明 |
|----------|:----------:|:--------:|:------:|------|
| 侧栏多开聊天 | 是 | **否** | 否 | 人决定何时点下一聊 |
| Git Worktree / `/worktree` | 是（工作区隔离） | 否 | 否 | 为**并行**防互踩，不排队 |
| `/best-of-n` | 是（多 worktree） | 否 | 部分 | 同题竞赛，不是任务依赖 |
| 计划 + **Build in Parallel** | 弱（同计划） | **部分** | 弱 | [官方](https://cursor.com/help/ai-features/multi-agent)：独立步并行，**依赖步按序** |
| 子 Agent（Subagents） | **是**（独立窗口，结果回父会话） | **部分** | 弱 | 父会话编排；默认可 batch-wait；`/multitask` 改为异步并行 |
| Agents Window + Cloud | 是 | 否（默许并行） | **是** | 可交云端、手机/Web 看，不必守本机 |
| `/in-cloud`、`/babysit` | 是 | 否 | **是** | 长任务上云，本机继续干别的 |
| Cloud Agent **同一 agent 多 run** | **否**（同一对话状态） | **是** | 是 | [API](https://cursor.com/docs/cloud-agent/api/endpoints)：一 agent **同时只能一个 run**；忙则 409。这是「同一上下文串行追问」，不是新会话 |
| Cloud Agent **多个 agent** | **是** | **需自建** | 是 | 官方不提供跨 agent 依赖图；你轮询 A 的 run 结束后再 `create agent` B |
| Automations | 是（每次新 Cloud Agent） | **事件串行** | **是** | PR 合并 / CI / Webhook / Linear 状态等触发下一任务 |
| Hooks `stop` + `followup_message` | **否** | 同会话续跑 | 部分 | [Hooks](https://cursor.com/docs/hooks.md) 只自动再发**本会话**下一条，**不会开新聊天** |
| Cursor CLI `agent` + `--worktree` | 是 | 需脚本 | 是 | 可写「等 A 退出码再起 B」 |

**一句话**：官方**没有**「聊天队列 / 会话依赖」。官方**有**「计划内依赖」「同 Agent 禁止并发 run」「用 Git/Webhook 拉起下一个云端 Agent」。

## 和需求最接近的官方路径（深挖）

### 1. 计划里的依赖步（IDE 内、同一上下文族）

适用：本来就是一件大事拆成几步，后步必须用前步产物，但你不坚持「必须是两个聊天窗口」。

- 在 Agents Window / 计划里写清依赖。
- **Build in Parallel** 只并行无依赖步，有依赖的保持顺序。
- 代价：上下文仍挂在这条计划/会话上；很长时要靠摘要，不是全新聊天。

### 2. 父会话 + 子 Agent（官方推荐的「不同上下文」）

适用：要隔离上下文，但接受**一个总控会话**盯着依赖。

- 子 Agent 自带独立 context，做完把结果交回父会话。
- 父会话可以「先 spawn 调查子 Agent，等结果再 spawn 施工子 Agent」——这是**会话内串行编排**，不是两个对等聊天互锁。
- 论坛有人把「并行子 Agent」当编排器，官方口径更接近：**子 Agent 是委派，不是 N 个长工各自开 PR 的调度器**；后者更适合 Cloud Agents。

### 3. 云端 Agent + 不值守

适用：你要离开电脑。

- 本机聊到可交割处，handoff 到 Cloud；或 Agents Window 直接开云端。
- **不解决**「B 等 A」；只解决「A 很长时你不用守着」。
- 同一 Cloud Agent 上追加 prompt：官方强制 **run 串行**（忙则 409）。这是「同一上下文的队列」，不是多会话。

### 4. Automations：用仓库事件当门闩（最接近「不同上下文 + 不值守 + 串行」）

适用：完成条件能落到 Git / CI / Linear / Webhook。

典型链：

1. 会话 A（或 Cloud Agent A）做完并开 PR。
2. Automation：「PR merged」或「CI completed」→ 启动 **新的** Cloud Agent，prompt 写任务 B。
3. 你不在场；B 是全新上下文。

Webhook：内部脚本在 A 的 hook/`stop` 或 CI 成功时 POST，拉起 B。这是官方支持的触发面，编排逻辑在你这边。

### 5. Cloud Agents API：自建 DAG

适用：完成条件是「A 的 run 结束」而不是「PR 合了」。

- `create agent` + 轮询 run 状态（或 SSE）。
- A 结束后再 `create agent`（新上下文）或对 B `create run`。
- **官方提供可编程面，不提供现成队列 UI。**

### 6. 明确不是跨会话串行的能力

- **`/loop`（本机 Skill）**：同一会话按间隔/事件醒来，不是官方「多聊天调度」。
- **Hooks `stop`**：续写本会话，误用会变成无限续聊。
- **Worktree**：隔离并行写盘，不会挡住另一聊天的「发送」。

## 社区信号（非官方承诺）

- 论坛有「长任务编排 / 根 Agent + 子 Agent + 多 PR」讨论：官方侧建议独立长任务用 **Cloud Agents**，不要把 `.cursor/agents` 子 Agent 当集群调度器。
- 并行子 Agent 的 batch-wait 被当成性能问题讨论——说明运行时更偏向「一批并行再等齐」，而不是「跨聊天 FIFO 队列」。

---

## 调查结论

1. **官方没有**「多个对等 IDE 会话按依赖自动开下一个」的开关或设置页。
2. **官方已经覆盖**你需求的拆解件：隔离（Worktree / 子 Agent / 新 Cloud Agent）、顺序（计划依赖、同 Agent 单 run、Git/Webhook 事件）、不值守（Cloud / Automations）。
3. 要同时满足「对等的不同聊天 + 硬串行 + 不值守」，当前只能：**Automations 事件链** 或 **Cloud API 编排**；本地多开聊天仍需人点，或自己写「A 结束后调 CLI/`agent` 起 B」。
