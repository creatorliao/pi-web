## 结论先行

同类产品几乎都把「自动起标题」做成**默认后台任务**，而不是主路径上的按钮。常见配方是：新会话先用占位（New Chat / 首条原文），**第一次对话产生内容后**用一次小模型或当前模型摘要，写入标题后停止。用户改名应当锁死自动改写——ChatGPT 后来反复改用户标题，社区投诉很多，这是反面教材。技术上要单独处理：输出格式、任务模型、触发时机、失败回退。

---

## 1. 行业里在解决什么

历史列表不能全是「新对话」。标题要短、跟用户语言、能检索。实现上多半是**另开一次 completion**，不跟主回复抢同一条 stream。

三件必须分开的事：

1. **展示占位**：还没有正式标题时列表里写什么。
2. **自动写入**：何时、用什么上下文、写几次。
3. **所有权**：机器写的能不能再改；人写的能不能被机器改。

## 2. 各家做法

### 2.1 Open WebUI

- **默认开**：后台任务「Title Generation」，可用环境变量关掉。
- **时机**：跟在 chat completion 事件后面；首条若取消，标题可能不生成。
- **模型**：单独 Task Model。文档明确劝：不要用旗舰或长思考模型去写三五个词，贵且慢。
- **输出**：演进后要求 JSON `{ "title": "…" }`；自定义提示词若没写 JSON，解析失败就退回**首条用户消息**。Issue #16462、Discussion #9567 / #10216 大量「生成了但界面仍是第一句」——根因是解析合同变了，失败静默回退。
- **上下文**：默认提示里用最近消息模板（如 `{{MESSAGES:END:2}}`），不是整段超长历史。
- **对本仓**：我们已有纯文本 + JSON 双解析，比「只认 JSON」稳；缺的是默认触发和可选廉价模型。

文档：[Open WebUI Essentials](https://docs.openwebui.com/getting-started/essentials/)；提交 [5420c16](https://github.com/open-webui/open-webui/commit/5420c165c60edb23a841f1b469d2fec381775cbf)。

### 2.2 LibreChat

配置键写在 `librechat.yaml` 各 endpoint / `endpoints.all`：

| 键 | 含义 |
|----|------|
| `titleConvo` | 是否自动生成（文档默认 false，部署常打开） |
| `titleTiming: immediate` | 请求一开始就并行，只用**第一条用户消息**，标题快 |
| `titleTiming: final` | 等主回复结束再生成（旧行为） |
| `titleModel` / `titleEndpoint` | 廉价模型或另一家供应商 |
| `titleMethod` | completion 或 structured |
| `titlePrompt` | 必须含 `{convo}` |

逻辑：自动是默认产品期望；时机在「快（只看第一句）」和「准（看完一轮）」之间可配。Discussion #6314：主回复失败时标题卡在 New Chat；维护者说**成功完成的第一轮只做一次**，之后靠用户手改。社区希望失败也用第一句补标题（ChatGPT 有类似重试）。

文档：[Shared Endpoint Settings](https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/shared_endpoint_settings)。

### 2.3 LobeChat

- PR #1888：按首条消息用当前模型生成 topic 名；设置项 `enableIntelligentTopicName`。
- 发送路径里 `summaryTitle()`：新 topic 或当前 topic **还没有 title** 才摘要。
- PR #16467：先乐观插入一行占位 topic，**等摘要完成再替换一次**，避免标题闪成 `...`。

门控是「title 为空」，不是「每次回复都改」。和本需求的「没手工名才自动」同一结构。

源码线索：[generateAIChat.ts](https://github.com/lobehub/lobe-chat/blob/3be609c3/src/store/chat/slices/aiChat/actions/generateAIChat.ts)。

### 2.4 ChatGPT（消费级对照）

- 默认自动标题，列表可手改。
- 社区（2025–2026）持续抱怨 **Proactive naming 覆盖用户改过的标题**，以及长会话标题跟着话题漂移。诉求是 lock title。
- 教训：**自动可以默认开，覆盖用户名不行。** 本仓应做成硬门控，不要学「智能持续改名」。

### 2.5 编程助手（Cursor / Claude / 本仓同源 pi）

公开仓库里很少把「会话标题算法」写成独立文档。常见是文件名 / 首条提示截断，或产品侧一次摘要。pi-web **已经比多数 TUI 多走了一步**（独立生成器 + 清洗 tool 历史）。差距只在「要不要默认跑」。

## 3. 横切对比

| 维度 | 常见做法 | 本仓现状 | 建议对齐 |
|------|----------|----------|----------|
| 默认 | 开，后台跑 | 关，要点按钮 | 改为默认自动 |
| 时机 | immediate（首句并行）或 final（一轮结束） | 无自动时机 | 一期 **final**：已有 `waitForIdle`，agent 会话工具多，首句并行容易残缺 |
| 次数 | 通常一次 | 按钮可无限覆盖 | 自动只在持久化名为空时 |
| 手工 | 应锁定 | 按钮会覆盖 | 自动跳过已有名；按钮是否覆盖单列待决 |
| 上下文 | 首句，或首轮 user+assistant，或最近 2 条 | 清洗后的**整段**历史 | 一期沿用整段（压缩后仍有摘要）；若费用高再截断 |
| 模型 | 小 / 快 / 非 reasoning | 当前会话模型 + thinking | 一期复用；二期再 Task Model |
| 失败 | 回退首条原文或 New Chat | 按钮报错，展示仍用回退 | 自动失败静默，保持回退 |
| 解析 | JSON 易碎 | 纯文本 + JSON | 保持现解析 |
| 占位稳定性 | 乐观标题，一次替换 | 回退首条，生成后替换 | 生成成功再改持久化名，列表自然刷新 |

## 4. 技术细节（施工时用）

**该不该和主回复共用一条消息。** 本仓若历史以 user 结尾，会把标题指令折进最后一条 user 再 `continue()`，避免 `user,user`。LibreChat immediate 则是**另一条短请求**，只带第一句。两种都能工作；我们已实现前者，自动触发时继续走它即可。

**工具残留。** Agent 产品比纯聊天更容易在「还在跑工具」时被拿去命名。本仓已 sanitize + waitForIdle。这是选 final 而不是 immediate 的主要理由。

**失败合同。** Open WebUI 把解析失败做成「看起来像第一句」，用户以为功能坏了。本仓应：**失败不写 `session_info`**，界面继续回退，必要时打一次错误态，不要把第一句当成生成成功。

**费用。** 同模型再跑一遍全历史，长会话不便宜。一期可接受（次数：每会话自动至多一次）。若用户开高 thinking，标题也会带 thinking——Open WebUI 专门警告过。`@待确认` 是否一期就关 thinking 或换小模型。
