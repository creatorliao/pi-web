## 目标（Why + What）

- **业务目标**：历史列表和对话顶栏能一眼认出会话，不必再点「生成标题」。
- **用户价值**：新对话发完第一轮就有可读标题；用户自己起的名字不被机器改掉。
- **成功标准**：
  1. 未手工命名的已落盘会话，在具备可命名内容后会自动写入标题，无需再点按钮。
  2. 已手工命名的会话，自动命名不会覆盖。
  3. 侧栏仍可用现有重命名入口改名；改名后自动命名不再介入。
  4. 未命名时的展示回退（首条用户消息截断）仍然可用，且**不能**被当成「用户已命名」。

## 功能需求（In Scope）

| # | 需求描述 | 优先级 | 来源 |
|---|----------|--------|------|

| F-02 | 会话尚无持久化名称时自动命名 | 必做 | 用户 |
| F-03 | 用户已手工写入名称时，自动命名跳过 | 必做 | 用户 |

| F-06 | 压缩后仍能命名（已有 `compactionSummary` / `messageCount` 路径，须保住） | 必做 | 现状，见 02 |
| F-07 | 失败时不破坏会话；界面可继续用首条消息截断作展示 | 必做 | 体验 |

## 非功能需求

- **费用**：自动命名会多一次模型调用；一期可复用现成 `generateSessionTitle`（与当前会话同模型）。是否换廉价任务模型标 `@待确认`。
- **并发**：同一会话同时只允许一次命名请求（现状 `autoNameStatus.kind === "naming"` 已挡按钮，自动路径须同样互斥）。
- **兼容**：Win/Mac 会话路径仍走 `SessionManager` / `session_info`，不另造标题库。
- **安全**：命名用的临时 Agent 继续禁用真实工具执行（现状 shadow tools）。

## 非目标（Out of Scope）

- 不把标题做成可点击就地编辑（R-03 顶栏已写「本轮不做重命名」；本专题不扩这个交互）。
- 不做 ChatGPT 式「话题变了就反复改标题」。
- 一期不强制上独立 Task Model / 表情标题 / JSON 强制输出（现成解析已兼容纯文本与 JSON）。
- 不改会话文件主格式以外的存储（不另建 SQLite 标题表）。

## 约束

- 先文档、后代码；本轮只落盘，等确认再施工。
- 持久化名称只有 `session_info` / `setSessionName` 这一条链；展示名还有「首条消息 50 字 / id 前 12」回退，二者必须分开判断。
- 侧栏「未改动就提交」刻意不把回退文案写成正式名，自动命名逻辑必须尊重这一点。
