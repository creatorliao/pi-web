---

## 1. 真实意图（用户要的是什么）

用户用 PARA 管知识，但**不是四维都「一个主题一个文件夹」**。

1. **每一次输入的需求、方案**（以及同主题的任务、调查、改善报告）属于**有起止的专题**，必须进 **`docs/01-Projects/<R日期-序号-主题>/`**，同一主题的多份稿放在**同一个项目夹**里，用 `00-README`、`01-需求_…`、`02-方案_…` 编号，**不要再套一层主题子目录**。
2. **`02-Areas` / `03-Resources` / `04-Archives` 禁止为新主题再建子文件夹**。领域规范、长期笔记、剪藏都是**该维根下的单文件**（`YYYYMMDD-xx-主题.md`）。归档时可以把整个项目夹从 Projects **整夹迁入** Archives，那是迁移，不是在 Archives 根下为新主题 mkdir。
3. 希望 **下一次** 用本技能「创建目录结构」或「优化/补全目录结构」时，**把上述规则同时写进消费仓的 `AGENTS.md`**，让后续智能体只读 `AGENTS.md` 就不会再把需求/方案摊到 Areas，也不会在 Areas 里建主题夹。

一句话：**Projects 用主题夹；另外三维扁平文件；规则要进消费仓 AGENTS，而不是只写在 PARA 的 README。**

---

## 2. 遇到的问题（消费仓现场）

### 2.1 现象

`pi-web` 的 `AGENTS.md` 曾写成：

- 四维目录**一律**「根下直接放文件，不要再 mkdir」；
- 明确写「对 `01-Projects` 同样适用」；
- 日常写需求/方案 **不要** `para-structure cp`，也 **不要** 手建 `R{YYYYMMDD}-xx-标题/`，除非用户口头点名 CLI。

后果：智能体把成对的「需求 + 方案」写成 Areas 根下的扁平文件，例如：

```text
docs/02-Areas/20260819-05-历史与系统提示进文件区-需求.md
docs/02-Areas/20260819-06-历史与系统提示进文件区-方案.md
（2026-08-19 已按主题迁入 docs/01-Projects/R20260819-09-历史与系统提示进文件区/）
```

而同一仓库里，早期用 `para-structure cp` 建的专题是正确形态：

```text
docs/01-Projects/R20260819-03-界面Cursor化布局/
  00-README.md
  01-需求_….md
  03-方案_….md
```

同一类交付物出现两套落盘，后续 Agent 会继续学错的那套（Areas 扁平需求/方案）。

### 2.2 根因（产品侧缺口，不是用户口误）

| 缺口 | 说明 |
|------|------|
| **规则写反且写全** | 消费仓 AGENTS 把「Areas 不要主题夹」推广成「四维都不要主题夹」，直接否定了 `cp` 的存在理由。 |
| **init 只写 PARA README** | `para_readme.py` 的 `docs/README.md` 只解释四维用途和 `R日期-序号-标题`，**不写「需求/方案必须进 Projects」**，也不写「Areas/Resources/Archives 禁止主题子夹」。 |
| **消费仓 AGENTS 不是 init/doctor 产出** | `init` / `doctor --fix` 补四维目录、`.gitkeep`、PARA `README.md`，**不创建、不补丁仓库根 `AGENTS.md`**。业务仓（如 Next.js 的 pi-web）自己的 `AGENTS.md` 由人/别的 Agent 写，容易和 PARA 打架。 |
| **Skill 未要求同步 AGENTS** | D00/D02 在 init 后只提醒读 PARA 根 `README.md`，没有「把落盘铁律写入/合并到消费仓 AGENTS」这一步。 |
| **医生只修骨架不修约定** | `doctor` 检测缺目录/缺 gitkeep/缺 README，**不检测**「AGENTS 是否写了错误的四维扁平规则」或「是否缺失 PARA 落盘节」。 |

当前产品仓已有「本仓库自己的 AGENTS」（Skill+CLI 同仓纪律），与「**被 init 的消费工作区**里给业务 Agent 看的 AGENTS」是两件事。后者缺失。

## 3. 消费仓已采取的解决办法（临时，须产品化）

已在 `D:\code\pi-web\AGENTS.md` 手工改成「按维分流」：

- `01-Projects`：**要**主题夹；需求/方案进夹，可用 `para-structure cp`，仅说「写需求/方案」也可手建同名 `R…` 夹。
- `02-Areas` / `03-Resources` / `04-Archives`：**不要**为主题 mkdir；单文件 `YYYYMMDD-xx-主题.md`。
- 正反例写清：Areas 里的 `…-需求.md` 是错的。

这只修正了 **pi-web 这一仓**。下一次在别的仓 `init` / `doctor`，还会再错，除非产品把同一节做成默认产出。

参考正文（消费仓现行约定，产品实现时应收敛为模板，而不是复制 pi-web 全文）：见仓库 `AGENTS.md` 的「docs / PARA 落盘约定」。

## 4. 期望修改（给 para-structure-master 的需求）

下列按优先级。实现时走产品仓既有节奏：**先记账 R01 → CLI + pytest + API → Skill D00/D02 双写**；结构约定同步改 `技术规范_*` 与产品仓自己的 `AGENTS.md`。

### 4.1 必做 · init / doctor 写入消费仓 AGENTS.md

**目标**：用户说「初始化 PARA」「结构坏了帮我补全/优化」时，除四维目录外，在**工作区协作入口**留下 PARA 落盘铁律。

建议行为：

1. **锚点**：消费仓仓库根的 `AGENTS.md`（与 PARA 根可能是 `./docs` 不是同一层）。  
   - 场景 A（`init -id`）：PARA 在 `docs/`，AGENTS 在**仓库根**（`docs` 的上一级）。  
   - 场景 B（已在 docs 内 init）：AGENTS 仍优先写**仓库根**（docs 的父目录）；若父目录没有、且用户明确只要 docs 当根，再退化为 PARA 根旁或 docs 上级。  
   - 场景 C（当前目录直接 PARA）：AGENTS 写在 PARA 根（与四维目录同级）。
2. **已有 AGENTS.md**：不要整文件覆盖。插入或替换**可识别锚点块**，例如：

   ```text
   <!-- BEGIN:para-structure-agents -->
   …落盘约定正文…
   <!-- END:para-structure-agents -->
   ```

   与 Next.js 往 `AGENTS.md` 注入 `BEGIN:nextjs-agent-rules` 同类：可重复跑 `doctor --fix` 而不毁掉业务仓其它章节。
3. **没有 AGENTS.md**：创建仅含该锚点块（外加一句「本文件由 para-structure 维护 PARA 节」）。
4. **doctor**：  
   - 缺锚点块 → 视为不健康，`--fix` 时插入；  
   - 已有锚点块 → 用**当前产品模板**覆盖块内正文（约定升级可随 CLI 版本滚到消费仓）；  
   - 块外用户正文一律不动。

### 4.2 必做 · 模板正文必须写清「按维分流」

写入 AGENTS 的模板（以及应同步修订的 `para_readme.py`）至少包含：

| 规则 | 必须写进模板 |
|------|----------------|
| Projects | 需求、方案、同主题配套稿 → `01-Projects/R{YYYYMMDD}-xx-主题/` |
| 夹内 | 编号文件，禁止再套主题子夹 |
| Areas / Resources | 禁止主题子文件夹；`YYYYMMDD-xx-主题.md` 落在该维根 |
| Archives | 禁止为新主题 mkdir；允许整夹从 Projects 迁入 |
| 分流 | 明确禁止把需求/方案写成 `02-Areas/…-需求.md` |
| 创建夹 | 新建专题优先 `para-structure cp "主题"`；已有同主题夹则追加文件，不平行再开一夹 |

`docs/README.md` 与 AGENTS 块**不得互相矛盾**。现在 README 只说「每个子项目一个文件夹」，没说 Areas 禁止子夹，Agent 仍可能两边各写一套。

### 4.3 必做 · Skill 路由与话术

更新 `.cursor/skills/para-structure-master`（及发布后的 `~/.agents/skills`）：

| 场景 | 新增约定 |
|------|----------|
| S01～S04 init 成功后 | 中文汇总里写清：已更新消费仓 `AGENTS.md` 的 PARA 节（路径打出来） |
| S11 doctor --fix | 同样汇报是否写入/刷新了 AGENTS 锚点块 |
| D00「初始化会创建什么」 | 增加：消费仓 `AGENTS.md` 的 PARA 锚点块 |
| 智能体行为 | init/doctor 后提醒用户：业务 Agent 以该 AGENTS 节为准落盘 |

**不要**再暗示「四维都不要建夹」或「没有点名 CLI 就禁止建 R 夹」。

### 4.4 建议 · 检测错误落盘（doctor 增强，可二期）

可选：`doctor --json` 报告：

- `02-Areas/`、`03-Resources/` 下一层若出现**目录**（除可忽略名），记为 warning（不默认 `--fix` 删除，避免误伤）；
- 文件名匹配 `*-需求.md` / `*-方案.md` 且位于 Areas 根，记为 warning：「应迁入 01-Projects 主题夹」。

`--fix` **默认不搬文件**（搬文件是内容决策）。一期只写规则进 AGENTS；二期再考虑 `--fix --relocate` 之类确认门。

### 4.5 明确不做

- 不把消费仓整份 `AGENTS.md` 换成产品仓那份（产品仓 AGENTS 是 Skill+CLI 同仓纪律，消费仓只要 PARA 落盘节）。
- 不在 Areas 用 `para-structure cp` 建夹。
- 不强制业务仓删除已误放到 Areas 的历史文件（pi-web 里 05/06 等可另开迁移任务）。

## 6. 验收标准（到执行仓改完后怎么算成功）

在空目录或夹具仓：

1. `para-structure init -id` 后：存在 `docs/{01-04}`、`docs/README.md`，以及**仓库根** `AGENTS.md` 含 `BEGIN:para-structure-agents`（名称以实现为准），块内有按维分流表。
2. 根 `AGENTS.md` 先写一段业务说明再跑 `doctor --fix`：业务段仍在，仅锚点块被刷新。
3. 再跑一次 `doctor --fix`：幂等，无重复插入两份块。
4. Skill 文档写明：需求/方案 → Projects 主题夹；另外三维不建主题夹。
5. 用错误 AGENTS（「四维都禁止 mkdir，含 Projects」）跑 `doctor --fix` 后，错误句被块内新模板替换。

## 7. 经验提炼（给下次改技能的人）

1. **PARA 四维不是同一种「文件夹粒度」**。Projects = 主题夹；Areas/Resources = 扁平文件；Archives = 迁入整夹，不新建主题。漏写任何一侧，Agent 都会选错维。
2. **消费仓真正听的是根 `AGENTS.md`，不是 `docs/README.md`。** 只 init README，业务 Agent 仍按 AGENTS 把需求摊到 Areas。
3. **「禁止嵌套」必须限定范围。** 写「四维都不要子文件夹」等于废掉 `cp`，也会让「写需求/方案」无法按主题归档。
4. **对已有 AGENTS 只能锚点合并，不能整文件覆盖。** 业务仓（Next.js、课程仓）已有长 AGENTS，init 覆盖等于事故。
5. **doctor 应修「约定漂移」，不只修「缺目录」。** 目录齐了但规则写反，结构看起来健康，落盘仍然错。

## 8. 消费仓对照摘录（实现模板时可压缩）

以下为 pi-web 已验证、用户确认的分流表，产品模板应保持语义等价：

| 维 | 放什么 | 是否建主题子文件夹 |
|----|--------|-------------------|
| `01-Projects` | 每次输入的需求、方案及同主题配套稿 | **要**：`R{YYYYMMDD}-xx-主题` |
| `02-Areas` | 长期规范、领域笔记（无交付闭环） | **不要** |
| `03-Resources` | 外部参考、剪藏 | **不要** |
| `04-Archives` | 已结束项目整夹迁入 | **不要**为新主题 mkdir |

夹内示例：

```text
docs/01-Projects/R20260819-03-界面Cursor化布局/
  00-README.md
  01-需求_20260819_界面Cursor化布局.md
  02-方案_20260819_界面Cursor化布局.md
```
